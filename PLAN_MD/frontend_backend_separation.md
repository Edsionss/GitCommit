# CognitoOcean 前后端分离架构方案

## 1. 项目现状分析

### 1.1 当前架构
CognitoOcean 是一个基于 Electron + Vue + TypeScript 的桌面应用程序，目前采用的是传统的 Electron 架构模式：

- **前端**：Vue 3 + TypeScript + Ant Design Vue
- **后端**：Electron 主进程 + Node.js 服务
- **通信方式**：IPC (Inter-Process Communication)
- **数据存储**：SQLite 数据库

### 1.2 当前架构特点
- **优点**：
  - 开发简单，前后端代码在同一项目中
  - 数据访问直接，无需网络请求
  - 适合桌面应用场景

- **缺点**：
  - 前后端耦合度高，难以独立开发和测试
  - 扩展性受限，难以支持多客户端
  - 部署方式单一，只能作为桌面应用
  - 前后端代码混合，不利于团队分工

## 2. 前后端分离架构设计

### 2.1 分离原则
1. **职责分离**：前端负责UI展示和用户交互，后端负责业务逻辑和数据处理
2. **接口标准化**：通过 RESTful API 或 GraphQL 进行通信
3. **独立部署**：前后端可独立开发、测试和部署
4. **技术栈解耦**：前端和后端可选择不同的技术栈

### 2.2 架构方案

#### 方案一：Web 应用 + RESTful API
```
┌─────────────────┐    HTTP/HTTPS    ┌─────────────────┐
│   前端 Web 应用  │ ◄────────────► │   后端 API 服务   │
│   (Vue 3)       │                │   (Node.js/Express) │
└─────────────────┘                └─────────────────┘
                                           │
                                      ┌────▼────┐
                                      │ 数据库  │
                                      │(SQLite/ │
                                      │ MySQL/  │
                                      │PostgreSQL)│
                                      └─────────┘
```

**特点**：
- 前端改为 Web 应用，可通过浏览器访问
- 后端提供 RESTful API 服务
- 数据库可选择 SQLite、MySQL 或 PostgreSQL
- 支持多客户端访问（Web、移动端等）

#### 方案二：桌面应用 + 微服务架构
```
┌─────────────────┐    HTTP/HTTPS    ┌─────────────────┐
│   桌面客户端     │ ◄────────────► │   API 网关       │
│   (Electron+Vue) │                │                 │
└─────────────────┘                └────────┬────────┘
                                              │
                                   ┌──────────▼──────────┐
                                   │   微服务集群         │
                                   │  ┌─────────────┐    │
                                   │  │ 用户服务     │    │
                                   │  └─────────────┘    │
                                   │  ┌─────────────┐    │
                                   │  │ 审计日志服务 │    │
                                   │  └─────────────┘    │
                                   │  ┌─────────────┐    │
                                   │  │ 股票服务     │    │
                                   │  └─────────────┘    │
                                   └─────────────────────┘
                                              │
                                      ┌───────▼───────┐
                                      │    数据库      │
                                      │ (可分库分表)   │
                                      └───────────────┘
```

**特点**：
- 保持桌面客户端形态
- 后端采用微服务架构，通过 API 网关统一入口
- 各服务独立部署和扩展
- 数据库可分库分表，提高性能和可靠性

#### 方案三：混合架构（推荐）
```
┌─────────────────┐    HTTP/HTTPS    ┌─────────────────┐
│   桌面客户端     │ ◄────────────► │   后端服务       │
│   (Electron+Vue) │                │   (Node.js)     │
└─────────────────┘                └────────┬────────┘
                                              │
                                   ┌──────────▼──────────┐
                                   │   业务逻辑层        │
                                   │  ┌─────────────┐    │
                                   │  │ 用户管理     │    │
                                   │  └─────────────┘    │
                                   │  ┌─────────────┐    │
                                   │  │ 审计日志     │    │
                                   │  └─────────────┘    │
                                   │  ┌─────────────┐    │
                                   │  │ 股票数据     │    │
                                   │  └─────────────┘    │
                                   └─────────────────────┘
                                              │
                                      ┌───────▼───────┐
                                      │    数据库      │
                                      │ (SQLite/MySQL)│
                                      └───────────────┘
```

**特点**：
- 保持桌面客户端形态，但重构内部架构
- 后端业务逻辑独立，通过 API 提供服务
- 前端通过 HTTP 请求与后端通信，而非 IPC
- 保留桌面应用特性，同时具备 Web 应用的灵活性

## 3. 推荐方案详细设计

### 3.1 整体架构
采用**方案三：混合架构**，在保持桌面应用形态的同时，实现前后端分离。

### 3.2 前端架构
```
src/renderer/src/
├── api/                 # API 调用层
│   ├── index.ts         # API 请求封装
│   ├── auditLog.ts      # 审计日志 API
│   ├── user.ts          # 用户 API
│   └── stock.ts         # 股票 API
├── components/          # 组件
├── views/               # 页面
├── stores/              # 状态管理
├── router/              # 路由
└── utils/               # 工具函数
```

**关键改造点**：
1. 将 IPC 调用改为 HTTP 请求
2. 使用 axios 或 fetch 进行 API 调用
3. 统一错误处理和请求拦截
4. 实现 Token 认证和权限控制

### 3.3 后端架构
```
src/backend/
├── server.ts            # 服务器入口
├── routes/              # 路由定义
│   ├── index.ts         # 路由入口
│   ├── auditLog.ts      # 审计日志路由
│   ├── user.ts          # 用户路由
│   └── stock.ts         # 股票路由
├── controllers/         # 控制器
│   ├── auditLog.ts      # 审计日志控制器
│   ├── user.ts          # 用户控制器
│   └── stock.ts         # 股票控制器
├── services/            # 业务逻辑
│   ├── auditLog.ts      # 审计日志服务
│   ├── user.ts          # 用户服务
│   └── stock.ts         # 股票服务
├── models/              # 数据模型
│   ├── auditLog.ts      # 审计日志模型
│   ├── user.ts          # 用户模型
│   └── stock.ts         # 股票模型
├── middleware/          # 中间件
│   ├── auth.ts          # 认证中间件
│   └── error.ts         # 错误处理中间件
└── utils/               # 工具函数
```

**关键改造点**：
1. 使用 Express 或 Koa 框架构建 Web 服务
2. 实现 RESTful API 接口
3. 添加认证和授权机制
4. 统一错误处理和日志记录

### 3.4 数据层设计
```
src/backend/database/
├── index.ts             # 数据库连接
├── migrations/          # 数据库迁移
├── seeds/               # 种子数据
└── utils/               # 数据库工具
```

**关键改造点**：
1. 使用 ORM 框架（如 Prisma、TypeORM）
2. 实现数据库迁移机制
3. 支持多种数据库（SQLite、MySQL、PostgreSQL）
4. 数据访问层与业务逻辑层分离

## 4. 实施步骤

### 4.1 第一阶段：后端服务独立
1. 创建后端服务目录结构
2. 实现 HTTP 服务器和基础路由
3. 将现有业务逻辑从主进程迁移到后端服务
4. 实现数据库访问层
5. 提供基础的 RESTful API

### 4.2 第二阶段：前端改造
1. 重构前端 API 调用层，将 IPC 调用改为 HTTP 请求
2. 实现请求拦截器和错误处理
3. 添加认证和授权机制
4. 优化前端状态管理

### 4.3 第三阶段：集成与测试
1. 前后端集成测试
2. 性能优化和安全加固
3. 文档完善和代码规范
4. 部署和发布流程优化

## 5. 技术选型

### 5.1 后端技术栈
- **Web 框架**：Express.js 或 Koa.js
- **ORM 框架**：Prisma 或 TypeORM
- **认证授权**：JWT (JSON Web Token)
- **API 文档**：Swagger/OpenAPI
- **日志管理**：Winston 或 Morgan
- **测试框架**：Jest 或 Mocha

### 5.2 前端技术栈
- **HTTP 客户端**：Axios
- **状态管理**：Pinia
- **路由**：Vue Router
- **UI 组件**：Ant Design Vue
- **表单处理**：VeeValidate
- **测试框架**：Vitest 或 Jest

### 5.3 数据库选择
- **开发环境**：SQLite（轻量级，便于开发）
- **生产环境**：MySQL 或 PostgreSQL（高性能，高可用）

## 6. 预期收益

### 6.1 开发效率提升
- 前后端可并行开发，缩短开发周期
- 接口标准化，减少沟通成本
- 独立测试，提高代码质量

### 6.2 系统可维护性增强
- 代码结构清晰，职责分明
- 模块化设计，便于维护和扩展
- 统一错误处理和日志记录

### 6.3 系统可扩展性提高
- 支持多客户端（Web、移动端等）
- 微服务架构，便于水平扩展
- 灵活的技术选型，适应业务变化

### 6.4 部署灵活性增强
- 前后端可独立部署
- 支持容器化部署（Docker）
- 便于 CI/CD 流程集成

## 7. 风险与挑战

### 7.1 技术风险
- 前后端分离后，网络通信可能带来性能问题
- 需要处理跨域、认证等 Web 应用常见问题
- 数据一致性保障更加复杂

### 7.2 开发挑战
- 团队需要适应新的开发模式
- 接口设计和版本管理需要规范
- 测试策略需要调整，增加接口测试

### 7.3 运维挑战
- 部署架构更加复杂
- 需要监控前后端服务状态
- 日志收集和分析更加复杂

## 8. 总结与建议

CognitoOcean 项目采用前后端分离架构，可以显著提高系统的可维护性、可扩展性和开发效率。推荐采用混合架构方案，在保持桌面应用形态的同时，实现前后端分离。

实施过程中，建议分阶段进行，先完成后端服务独立，再进行前端改造，最后进行集成与测试。同时，需要重视接口设计、错误处理、认证授权等关键环节，确保系统稳定可靠。

通过前后端分离，CognitoOcean 将具备更好的扩展性，未来可以轻松支持 Web 版本、移动端版本，为产品发展奠定坚实的技术基础。
