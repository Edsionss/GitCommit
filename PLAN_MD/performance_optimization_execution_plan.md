# 性能优化执行任务清单

本文档根据《性能优化方案》制定，旨在列出具体、可执行的代码层面任务步骤。我将在获得您的批准后，严格按照此清单顺序执行。

---

### **阶段一：构建与打包优化**

此阶段的目标是减小最终打包体积，加快应用的初始加载速度。

*   **任务 1.1：安装打包分析工具**
    *   **操作**: 执行 `pnpm add -D rollup-plugin-visualizer` 命令。
    *   **目的**: 安装依赖，为下一步的可视化分析做准备。

*   **任务 1.2：配置 Vite 以生成分析报告**
    *   **文件**: `electron.vite.config.ts`
    *   **操作**: 我将修改此文件，在 `renderer` 的 `plugins` 数组中添加 `visualizer` 插件的配置。
    *   **目的**: 使得每次执行 `pnpm build` 时，都能生成一个 `stats.html` 文件，直观展示各模块体积占比。

*   **任务 1.3：分析并确定懒加载路由**
    *   **文件**: `src/renderer/src/router/index.ts`
    *   **操作**: 我将首先读取此文件内容，分析出所有未使用动态导入 (`import()`) 的路由。
    *   **目的**: 确定所有可以被懒加载优化的组件，为下一步重构做准备。

*   **任务 1.4：实施路由懒加载**
    *   **文件**: `src/renderer/src/router/index.ts`
    *   **操作**: 我将把任务 1.3 中确定的所有静态导入的组件，全部修改为 `() => import(...)` 的动态导入形式。
    *   **目的**: 将非核心页面的代码从主包中分离出去，显著减小初始包体积。

---

### **阶段二：主进程优化**

此阶段的目标是加速主进程的启动，减少应用白屏时间。

*   **任务 2.1：分析主进程的模块导入**
    *   **文件**: `src/main/index.ts`
    *   **操作**: 我将读取并分析此文件，寻找在文件顶部导入、但只在特定函数（如 `createWindow`）或事件回调中使用的模块（例如 `shell`, `dialog`）。
    *   **目的**: 识别出可以被延迟加载的模块。

*   **任务 2.2：实施主进程模块懒加载**
    *   **文件**: `src/main/index.ts`
    *   **操作**: 对于上一步确定的模块，我会将其 `import` 语句移动到实际使用它的函数或代码块内部。
    *   **目的**: 避免在启动时加载非必需模块，加快 `app.whenReady()` 事件的触发速度。

---

### **阶段三：渲染器进程优化**

此阶段的目标是提升 UI 渲染性能和用户交互的流畅度。

*   **任务 3.1：识别长列表组件**
    *   **文件**: `src/renderer/src/components/SystemTools/SystemStartupManager.vue` (作为示例)
    *   **操作**: 我将分析此组件，它使用 `a-table` 来渲染一个列表，这是一个潜在的性能瓶颈。
    *   **目的**: 确定一个适合进行虚拟化改造的目标。

*   **任务 3.2：对长列表实施虚拟化**
    *   **文件**: `src/renderer/src/components/SystemTools/SystemStartupManager.vue`
    *   **操作**: 我将使用 Ant Design Vue 自带的 `virtual` 属性。我会修改 `a-table` 组件，为其开启虚拟滚动功能。
    *   **目的**: 作为示范，将一个长列表改造为虚拟滚动，极大提升其渲染性能。

---

### **阶段四：IPC 通信优化**

此阶段的目标是降低主进程与渲染器进程间的通信开销。

*   **任务 4.1：分析现有 IPC 接口**
    *   **文件**: `src/preload/index.ts`
    *   **操作**: 我将通读此文件，寻找所有返回大量数据数组的 `ipcRenderer.invoke` 调用，例如 `getSystemStartupApps`, `getRepoAuthors` 等。
    *   **目的**: 找出潜在的大数据量、同步等待的通信瓶颈。

*   **任务 4.2：将一个“即发即忘”的通信改造为单向模式**
    *   **分析**: 目前项目中大部分是 `invoke/handle` 的双向调用。我会寻找一个合适的场景进行优化。
    *   **操作**: 我将以一个假设的“日志记录”功能为例，在方案文档中已提供代码。在实际执行中，我会寻找一个真实且合适的场景，例如 `removeSystemStartupApp` 后的“刷新列表”操作，可以考虑将其改为后端主动推送更新，而不是前端等待删除成功后再请求刷新。
    *   **目的**: 演示如何使用 `send` 代替 `invoke` 来减少不必要的等待和通信开销。
